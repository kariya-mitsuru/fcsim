## 1. 問題点・矛盾点

### 1-1 【中】`scripts/wsl-try.sh`: 後片付けに失敗しても「OK」になる

`cleanup()` は `set +e` の後に `rmmod tcm_fcsim && echo ...` を実行するが、失敗しても `rc` を変えない
（`scripts/wsl-try.sh:84-86`）。`fcsimctl host delete`・`fcsim-targetcli ... delete`・
`rmdir /sys/kernel/config/target/fcsim` の失敗も同じ。その結果、モジュールが読み込まれたまま
（あるいはバックストアが残ったまま）でも、dmesg に警告が無ければ最後に `wsl-try: OK` と表示される。
本物の WSL2 カーネルで「何も残さない」ことを約束するスクリプトなので、ここは失敗を報告すべき。

- `tests/wsl-try-guest.sh` の `leftovers()` は成功時の残り物を確かめるが、
  後片付けの途中で失敗する場合（例: I/O 中のディスクを udev が開いていて rmmod が EBUSY）は試していない
- 案: 各後片付けの失敗で `rc=1`。最後に `[ -d /sys/module/tcm_fcsim ]` などを確かめる

### 1-2 【中】`drop=rsp` のルールの下での TMR が、ドキュメントの説明と違う動きをする

`docs/design.md` §4 では `drop=rsp` を「target は実行するが応答が失われる」とし、「TMR も応答なしになる」と書いている。
ところが `fcsim_issue_tmr()`（`src/fcsim_ini.c` 715-723 行付近）は、`drop` が `none` 以外なら
**TMR を LIO に渡さずに**捨てる。そのため `drop=rsp` の下では ABORT TASK / LUN RESET が target で実行されない。
EH がエスカレートしても、target 側のコマンドは中止されずに動き続ける。
「応答だけ失われた」実機の状況（target はタスクを中止済みだが initiator は知らない）とは違う。

- 案: (a) `drop=rsp` のときは TMR を LIO に渡し、`queue_tm_rsp` の結果を捨てる。または
  (b) ドキュメントに「TMR はどちらの drop でも target に届かない」と明記する
- 併せて、TMR には `delay_ms` と `error` を適用しない（`fcsim_fault_eval()` の `tmr` の分岐）ことも
  design.md の障害注入の節に書いておくとよい

### 1-4 【低】`fcsimctl restore` は障害ルールの未知のキーを黙って捨てる

`restore_plan()` は `{k: f[k] for k in FAULT_ATTRS if k in f}` で既知のキーだけを拾う。
一方、`fault set` は未知の属性をエラーにする（`fault_check()`）。手で編集した JSON の
`"delay": 100` のような綴り間違いは、エラーにならずにルールから消える。host・zoning の未知のキーも同様。
「restore は入力を検証してから」という design.md の記述に合わせるなら、未知のキーは拒否するのが一貫する。

### 1-5 【低】`fcsimctl fault set` で既存ルールを更新すると、消費中の `count` が戻る

`fault_set()` は既存ルールの `count` を読み、`count=0` を書き、他の属性を書いてから、読んだ値を書き戻す。
読んでから書き戻すまでに I/O が `count` を消費していると、その分が「払い戻され」、指定より多く注入される
（例: `count=3` のルールに I/O が流れている最中に `fault set I T drop=rsp`）。
実害は小さいが、意図どおりにするなら、書き戻す直前に `count` を読み直すとよい
（その間は `count=0` なので値は動かない）。

### 1-6 【低】ドキュメントやコメントと実装の小さなずれ

- `tools/fcsimctl:62` のコメントにある `fcsim_faults_make_rule` という関数は存在しない（実際は `fcsim_faults_make_group`）
- `docs/design.md` のモジュールパラメータ表では `dbg_release_delay_ms` を「次の READ」としているが、
  実装（`fcsim_check_stop_free`）は READ_10 / READ_16 だけを見る（READ_6 / READ_12 は対象外）
- `fcp_packet_aborts` は `fcsim_eh_abort()` の入口で数えるので、ABTS を送らない場合
  （既に完了していた、ファブリックが保持中だった、FAST_IO_FAIL）も増える。design.md の
  「EH abort」という説明とは合っているが、実機の HBA の多くは送った ABTS を数える。どちらの意味かを明記するとよい
- `fcsim_fpin_parse()` は先頭に空白がある入力（`" li ..."`）を拒否する（`strsep` が空の kind を返すため）。実害は小さい

### 1-7 【低】shellcheck（-S warning）

コマンド置換を引用符で囲んでいない（`$(rport_of ...)`、SC2046）。`fpin-fcsim.sh:104` の `w` は `eval` で代入されるので、
SC2154 は誤検知。どれも WWPN や sysfs のパスに空白が入らない限り無害で、整理の候補にとどまる。

## 2. テストの不足（本題）

現在のテストは、正常系・障害注入・EH のエスカレーション・multipath・ゾーニング・FPIN・CLI まで幅広く押さえていて、
`dbg_*` パラメータで競合の窓を決定的に開く作りもよい。以下は、コードの経路のうちまだ通っていないもの、
または通ってもアサートしていないものを、危険度の順に並べたもの。

### 2-1 【高】切り離し済みのエクスチェンジに対する `write_pending`

`fcsim_write_pending()` → `fcsim_xchg_fetch_write_data()` が false を返したときの
`transport_generic_request_failure(se_cmd, TCM_CHECK_CONDITION_ABORT_CMD)`（`src/fcsim_tgt.c:170-181`）は、
どのテストでも決定的には通らない。LIO の失敗経路を `write_pending` コールバックの中から再入的に呼ぶ、
use-after-free・参照漏れの起きやすい経路。

- 案: `dbg_deliver_terminate` と同じ形の一回限りのノブ（例: `dbg_write_pending_terminate`）を足す。
  次の WRITE を `write_pending` の直前に EH abort 相当で切り離し、次を確かめる:
  WRITE が失敗または再試行されること、バックエンドにデータが書かれないこと
  （ramdisk の該当ブロックが変わらない）、セッションの drain が終わること（後片付けで止まらない）、splat が無いこと

### 2-2 【高】dev_loss_tmo の満了

全テストが `dev_loss_tmo=30` で、リンクを落とす時間はそれより短い。そのため次の経路が試されていない:
rport が `Not Present` になる → scsi_target と sd が削除される → 再ログインで同じ WWPN の rport が
（新しい sd として）戻る。

- 案: `dev_loss_tmo=3` で link down を 5 秒続ける。sd が消えること、link up 後に新しい sd が現れて I/O が通ること、
  `fcsimctl status` が追従することを確かめる。満了時に I/O が残っている場合
  （fast_io_fail_tmo を設定しない → `terminate_rport_io` が dev_loss の満了から呼ばれる）も試す
- multipathd 側では、パスの削除と再追加（`multipathd-fcsim.sh` にはパスの失敗と復帰しか無い）

### 2-3 【高】並行 I/O のストレス

I/O はすべて `dd` 1 本ずつ（multipath の writer も 1 MiB ずつ逐次）で、キュー深さは実質 1。
エクスチェンジの設計（`cmd->lock`、RCU、SLAB_TYPESAFE_BY_RCU、ref 2 本）が守るべき競合
（完了と EH abort、完了と logout、遅延タイマーと terminate）は、並行性が無いとほとんど起きない。

- 案: `fio --ioengine=libaio --iodepth=32 --numjobs=4 --verify=crc32c` 等を流しながら、
  別のループで次を不規則に繰り返す。KASAN / lockdep の下で splat が無いこと、verify が通ることを確かめる
  - link down / up
  - TPG の disable / enable
  - 障害ルールの作成・変更・削除（delay / drop / error、probability=10 など）
  - `issue_lip`、`sg_reset -d`
- 実行時間は 60〜120 秒で十分。`make test` に入れるなら、乱数の種を出力に残す

### 2-4 【高】ファブリックが保持中（delay）のコマンドの終了経路

`delay_ms` のテストは「遅れて届くこと」だけを見る。タイマーが仕掛かったままのエクスチェンジを
終了させる経路は、どれも試されていない:

- delay 中の link down（`fcsim_terminate_tport` → `fcsim_xchg_finish` の `held` → `timer_delete_sync`）
- delay 中の host 削除（`fcsim_iport_destroy` の `DID_NO_CONNECT`）
- delay 中の EH abort（`in_lio == false` の経路。drop=cmd では試されているが、タイマーが仕掛かっている場合は試されていない）
- タイマーの発火とログアウトの競合（`fcsim_deliver` のコメントにある、タイマーがログアウト前に nexus を見つけた場合）
- delay 中のルール削除（`kfree_rcu` 後もコマンドは保持され続ける）

例: `delay_ms=2000` で `dd` を始め、0.5 秒後に link down → link up で `dd` が成功し、データが一致すること。
同様に host の rmdir では `dd` が失敗し、splat が無いこと。

### 2-5 【中】EH の target reset が成功する経路

`fcsim_eh_target_reset()`（全 LUN への LUN RESET）は、`fault-fcsim.sh` の `drop=rsp`（全部）での
エスカレーションでしか通らず、そこでは TMR が捨てられるので必ず失敗する。成功して
`starget` 単位でエクスチェンジを終了する経路は試されていない。

- 案: LUN を 2 つ持つ target で、片方の READ を `dbg_release_delay_ms` で保持したまま `sg_reset -t`。
  両方の LUN で I/O が続けられること、別の target のエクスチェンジは終了しないことを確かめる

### 2-6 【中】EH 中の FAST_IO_FAIL

`fcsim_eh_abort()` / `fcsim_eh_block()` で `fc_block_scsi_eh()` が FAST_IO_FAIL を返す経路
（EH 中に rport が blocked になり、fast_io_fail_tmo が満了する）は試されていない。
例: `drop=cmd` でタイムアウトさせ、EH が始まったところで link down（fast_io_fail_tmo=2）。

### 2-7 【中】障害ルールの優先順位と `any`

`any` のルールは `cli-fcsim.sh` で `count=0`（効かない）の状態でしか作られない。次が試されていない:

- `any` が実際に全 target に効くこと
- 特定 target のルールが `any` より優先されること（`count` を使い切った特定ルールが `any` を隠し続けることも、仕様として固定しておく価値がある）
- ルールの削除や変更が、実行中の I/O にすぐ効くこと

### 2-8 【中】fabric を通した SCSI の意味論

データの経路は「全部読み書きして一致」しか見ていない。次は、コピーと結果の組み立て
（`fcsim_xchg_status`）の分岐なのに試されていない:

- residual: 割り当て長がデータより長い INQUIRY / MODE SENSE（underflow）、`scsi_set_resid` の値
- LIO 自身が返す CHECK CONDITION（容量を超える READ → ILLEGAL REQUEST / LBA OUT OF RANGE）と、
  センスの中身が sc に届くこと（注入したエラーは `fcsim_inject_error` の経路で、LIO のセンスとは別物）
- ログイン中の LUN マップ変更: UNIT ATTENTION（REPORTED LUNS DATA HAS CHANGED）と、
  `issue_lip` による追加 LUN の検出・削除 LUN の扱い（design.md §8 で挙動を説明しているのにテストが無い）
- LUN 番号 256 以上（`FCSIM_MAX_LUN` は 65536。フラット形式のアドレッシングになる）

### 2-9 【中】TPG 属性

試されているのは `generate_node_acls` だけ。次は試されていない:

- `demo_mode_login_only=0`: ACL 無しの initiator が dynamic ACL で LUN を見られ、`demo_mode_write_protect=1`
  （既定）のため WRITE が DATA PROTECT になる
- `prod_mode_write_protect=1`: 明示 ACL の initiator の WRITE が拒否される
- `cache_dynamic_acls`

いずれも qla2xxx と同じ既定値を選んだ根拠（design.md §2）に関わるので、既定値の挙動だけでも固定しておくとよい。

### 2-10 【中】ゾーニングと I/O・multipathd

- 書き込み中にゾーン変更でパスが外れ、戻る（commit 由来のログアウトで、I/O が `DID_TRANSPORT_DISRUPTED` になり再試行される経路）
- multipathd のパス数の追従（design.md §6 と stage3-plan で「未実装」と明記済み）
- link down 中の initiator には commit の RSCN が送られないこと（`fcsim_zone_rscn` の `fcsim_iport_online` の条件）

### 2-11 【中】FPIN のペイロードの中身

`fc-events.py` はイベントコードと `event_data` しか表示しないので、組み立てた ELS の中身
（detecting / attached WWPN、`event_count=5`、`threshold`、`period`、`severity`、port name list）は検証されていない。
FC transport の統計は event type しか見ないため、`count=5` を指定しても `fpin_li_loss_of_sync_count` は 1 増えるだけ
（テストもそれを期待している）。

- 案: `fc-events.py` で `FCH_EVT_LINK_FPIN` の vendor data（ELS のペイロード）をデコードし、各フィールドを比べる
- オフラインの target ポートについての FPIN（ドキュメントで「送れる」と明言している）

### 2-12 【低】資源の上限と入力の検証

- port_id の枯渇: iport と tport は合わせて 254 個まで。255 個目の mkdir（`ida_alloc_range` の ENOSPC）は未テスト
  （misc の 180 ポートで近くまでは行く）
- WWPN の表記: 大文字・全ゼロ・区切りの位置違いの拒否（`fcsim_parse_wwn`）。`12:34` しか試していない
- `fcsimctl restore` が途中で失敗したとき（検証を通ったがカーネルが拒否した）の `.before-restore` の書き出し。
  port_id の枯渇を使えば再現できる
- 同じ WWPN を持つ zone のメンバー重複の除去、`members` に空を書いたとき

### 2-13 【低】`race-fcsim.sh close` は競合の窓に入ったことを確かめていない

`abort` は `TASK_DOES_NOT_EXIST` を、`deliver` は `dbg: terminating` を dmesg で確かめているが、`close` は
`sleep 0.5` で close_session の中に居ると仮定するだけで、ログアウト側が `close_in_flight` を見て
`close_done` を待ったかどうかを確かめていない。タイミングがずれると、何も試さずに通ってしまう。

- 案: `dbg_close_delay_ms` が効いたとき、および `fcsim_tgt_logout` が `close_done` を待ったときに
  dmesg に一行出し、テストでその行を確かめる

### 2-14 【低】テスト基盤

- **カーネルのデバッグ機能**: `scripts/build-kernel.sh` は KASAN / PROVE_LOCKING / DEBUG_ATOMIC_SLEEP /
  DEBUG_LIST だけ。次を足すと、今のテストのままで検出力が上がる
  - `DEBUG_KMEMLEAK`: nexus・refusal・zoneset・fault の kmalloc の漏れは現状まったく検出されない。
    各テストの最後に `echo scan > /sys/kernel/debug/kmemleak` で確かめる
  - `UBSAN`
  - `DEBUG_OBJECTS_TIMERS` / `DEBUG_OBJECTS_WORK`: SLAB_TYPESAFE_BY_RCU のオブジェクトに対して、
    確保ごとに `timer_setup` している
- **`splat_check`** のパターン: `UBSAN:`、`Oops`、`general protection fault`、`refcount_t:`、`kmemleak`、
  `rcu: INFO: .* detected stall` を足す
- **ホスト上で動く速いテスト**: `fcsimctl` の純粋な関数（`wwn()`、`restore_plan()`、`zone_name_check()`、
  `fault_check()`）は VM 無しで試せる。`make check` として、shellcheck、py_compile、
  `scripts/checkpatch.pl --no-tree -f src/*` と一緒にまとめるとよい
- **モジュールの再読み込み**: insmod / rmmod を数十回繰り返し（ポートとゾーンを作って消す）、kmemleak と splat を確かめる。
  `teardown_all` はゾーンを消さないので、ゾーンが残っているときに rmmod が EBUSY になることも併せて確かめるとよい

| 6 | §1-2 TMR と drop=rsp | 実装を直す方に決定。`drop=rsp` では TMR を LIO に渡し、`queue_tm_rsp` の応答だけを捨てる（新しい状態 `FCSIM_TMR_LOST`。EH は tmr_timeout 後に ACK の参照を落とす）。`drop=cmd` は従来どおり TMR を届けない。`fault-fcsim.sh` で LIO の `scsi_lu/resets` を使い、drop=cmd では増えず drop=rsp では増えることを確かめる。design.md に TMR への `delay_ms`・`error` 不適用も明記 |

新しいテストで見つかった不具合: `devloss-fcsim.sh` で、dev_loss_tmo 満了後に同じ WWPN の rport が戻るとき
`fc_remote_port_add()` が FC transport の（`WQ_MEM_RECLAIM` でない）workqueue を flush し、`WQ_MEM_RECLAIM` の
`fcsim_fabric` から呼ばれていたため check_flush_dependency の WARNING が出た。`fcsim_fabric` を `WQ_MEM_RECLAIM` 無しにした。
また `sg_reset` が書き込み可で開くことによる udev の READ が `count=1` のルールを消費するため、`fault-fcsim.sh` の
TMR の段の前に `udevadm settle` を入れた。

あわせて §1-6 のうち design.md の `dbg_release_delay_ms`（READ(10) / READ(16)）を直した。
